# ボスの行動を設計したループにした（2026-09-12）

ユーザー指摘：「ボスの動きがうろうろしすぎて、プレイヤー側が隙を見出せません。
ボスごとに4～6パターンの行動をループするように設計してください。」

結果：**当てずっぽうの徘徊を全部やめた。** 各ボスは4〜6拍の決まった順番をひたすら繰り返す。
各拍は「その技が要る距離まで歩く → 溜める → 撃つ → 立ち止まって隙を晒す」。

## 1. なぜ隙が見えなかったか

前の実装は、技と技の間に **乱数で行き先を選んで歩き、乱数で跳んでいた。** 結果として

- 次に何が来るか読めない。順番はあったが、その間の動きが毎回違うので拍が取れない
- 立ち止まる時間が短く、しかも来るタイミングが不定
- 跳んでいる間は立ち撃ちの弾が下を通る。撃てる瞬間がさらに減っていた

**動き自体が多いことが問題ではなく、動きに意味が無いことが問題だった。**

## 2. 今の形

ロスターの各ボスが `routine` を持つ。1拍は3つの数値だけ。

```js
{ move: 'volley', from: 'far', rest: .9 }
```

- `move` 使う技
- `from` 撃つ前に立つ位置。プレイヤーから `near` 95px / `mid` 190px / `far` 300px
- `rest` 撃ったあと**何もせず立っている秒数**。これが隙

エンジンの状態は4つだけ。`walk-◯◯` → `tell-◯◯` → `◯◯` → `rest` → 次の拍。

**歩くのは行き先がある時だけ。** 目的地に着いたらその場で溜めに入る。アリーナが狭くて
指定の距離が取れない場合は、反対側へ回る。それでも駄目なら1.4秒で諦めて撃つ。壁に
押し付け続けない。

**跳ねるのをやめた。** 小跳びは削除。跳ぶのはスラム技と、その着地の衝撃波だけになった。

`pool`（持ち技一覧）は `routine` から読み出す形にした。二重管理をやめたので、
ロスターとエンジンが食い違いようがない。

## 3. 8体のループ

| ボス | 拍 | ループ |
|---|---|---|
| WARDEN | 6 | volley@far → wave@mid → dash@far → mortar@far → ring@near → slam@mid |
| TIDEBREAKER | 4 | wave@far → mortar@far → slam@mid → ring@near |
| COILHEAD | 5 | wall@far → volley@mid → dash@far → mines@mid → ring@near |
| ASHMAW | 4 | mortar@far → mines@far → dash@far → slam@mid |
| NULLPRIEST | 5 | ring@mid → volley@far → wall@far → volley@near → ring@far |
| GRAVELOCK | 4 | slam@mid → wave@far → dash@far → slam@near |
| SPARKWIDOW | 6 | dash@far → volley@mid → wall@far → dash@near → mines@mid → volley@far |
| OBSIDIAN CROWN | 6 | volley@far → wall@far → dash@far → ring@near → mortar@far → slam@mid |

NULLPRIEST は技を3つしか持たないが、**同じ技を違う距離から**撃つことで5拍にしてある。
変わるのは「何が来るか」ではなく「どこに居なければならないか」。

## 4. 実測

プレイヤーを置いたまま、満タンの装甲で2周させた結果。

| ボス | 1周 | 隙の平均 | 隙の最短 | 歩く時間 | 静止している割合 | 平均移動 |
|---|---|---|---|---|---|---|
| WARDEN | 23.2s | 0.94s | 0.80s | 0.75s | 77% | 50px/s |
| TIDEBREAKER | 13.7s | 0.89s | 0.80s | 0.36s | 87% | 27px/s |
| COILHEAD | 17.1s | 0.79s | 0.70s | 0.49s | 82% | 45px/s |
| ASHMAW | 14.6s | 1.06s | 1.00s | 0.36s | 83% | 33px/s |
| NULLPRIEST | 15.4s | 0.68s | 0.60s | 0.47s | 86% | 37px/s |
| GRAVELOCK | 17.1s | 1.23s | 1.10s | 0.79s | 73% | 55px/s |
| SPARKWIDOW | 18.5s | 0.66s | 0.60s | 0.47s | 80% | 62px/s |
| OBSIDIAN CROWN | 18.5s | 0.73s | 0.65s | 0.34s | 84% | 41px/s |

プレイヤーの走りは190px/s。ボスは27〜62px/sしか動かない。

**最短の隙は0.60秒。** セイバーは振り始めから0.16秒で当たり、一振り0.40秒なので、
間合いに居れば必ず1発入る。最初の調整では NULLPRIEST 0.52秒・SPARKWIDOW 0.47秒まで
短くなったので、この2体の `rest` を上げて全体を0.60秒以上に揃えた。

装甲が減ると隙も縮む（×1 → ×0.82 → ×0.68）が、**0.42秒を下回らない床を入れた。**
最後まで必ず入る隙が残る。

## 5. 検証

`npm test` 全97項目合格（3回連続）。ボス戦のテストを書き直した。

- ロスター8体すべてが4〜6拍で、実在する技と距離を指しており、隙が床以上あること
- `pool` が `routine` から読まれていて食い違わないこと。ループが一周して先頭に戻ること
- WARDEN が**2周続けて同じ順番**で撃ち、どの技も必ず溜めから入ること
- 装甲100% / 50% / 20% のいずれでも、**攻撃のあとには必ず隙があり、その間ボスは
  1pxも動かず、床に立っていること**
- 技と技の間、ボスは目的地へ歩くだけで、それ以外では1度も動かないこと
- 指定した距離まで実際に歩いて到達し、そこで溜めに入ること
- 突進とスラムの跳躍の間だけは技が体を持つこと

既存テストの `arena()` を、合成したボスではなく `_spawnBoss` が作る本物のボスを使う形に
直した。実物の体格と実物のループで測るようになった。

`qa/boss-motion.cjs` を書き直し、徘徊の統計ではなくループと隙を出すようにした。
ループが2周とも同じであること、最短の隙が0.55秒以上あること、静止している割合が
7割以上あることを自動判定する。

browser-smoke 17項目・browser-mouse 12項目合格。release-check 合格。
公開用ビルドは44ファイル 8.67MB で変わらず。

## 6. 調整するには

`assets/bosses.js` の `routine` だけを触ればいい。エンジンに個体の事情は無い。

- 隙を長くしたい → その拍の `rest` を上げる
- 近寄ってほしい → `from` を `near` にする
- 手数を増やしたい → 拍を足す（4〜6拍に収めるのはテストが見ている）
- ボス全体の下限を変えたい → `game.js` の `combat.bossRestFloor`
- 距離そのものを変えたい → `combat.bossBands`

## 7. 途中で見つけた入力の不具合（2026-09-12）

このループの検証中に、**画面上のパッドのタップが3回に1回落ちる**のを見つけた。ボスとは
無関係の、前からあった不具合。モバイル前提の Playables に出すゲームとしては見過ごせない。

### 症状
`qa/release-check.cjs` のタップ判定が50%の確率で落ちていた。テストの不安定さかと思ったが、
実ブラウザーで12回叩くと**4回跳ばなかった**。ゲームは動いていて、プレイヤーは接地していて、
それでも入力が無かったことになっていた。

### 原因
`ui.js` がボタンを離す処理を **requestAnimationFrame 2回ぶん遅らせていた。** 一瞬のタップが
ゲームに見られないまま消えるのを避けるためだが、**アニメーションフレームとゲームの歩進は
同じ速さではない。** 実測したログがこれ。

    2288.9 tick jump=false     ← ゲームの歩進
    2289.8 pointerdown → 押下
    2289.9 pointerup  → 解放を2フレーム後に予約
    2301.3 解放が実行された
    2307.0 tick jump=false     ← 次の歩進。押下はもう消えている

歩進は18.1ms間隔なのに、このブラウザーでは rAF がもっと速く回る。2回ぶん待っても11.4msしか
経たず、ゲームが一度も押下を見ないまま解放が走っていた。

### 直し方
遅延をやめ、**押下そのものをエンジン側でラッチする**形にした。`setInput(a,true)` は
`input` を立てると同時に `pressed` にも印を付ける。歩進はその印を読んだら消す。
これで、どれだけ短いタップでも必ず1回は読まれ、1フレームより長くは残らない。

マウスの射撃・セイバーには既に同じ考え方（`pendingShoot` / `pendingSaber`）が入っていた。
それを全アクションに広げた形で、新しい仕掛けではない。`ui.js` 側の rAF 二段待ちは削除した。

### 検証
実ブラウザーで12回叩いて**12回とも跳んだ**（直す前は12回中4回が無反応）。
`release-check` は3回連続で合格（直す前は2回に1回落ちていた）。
常設テストを2件追加した。1つは jump / dash / shoot / saber のすべてについて
**歩進と歩進の間で始まって終わったタップが効くこと**、もう1つは
**押しっぱなしが1回の押下に潰れていないこと**。
